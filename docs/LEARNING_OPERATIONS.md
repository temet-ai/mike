# Learning recovery and weekly efficiency review

Mike's learning path is capture → genuine feedback → durable proposal → reviewed lesson → relevant delivery → observed outcome. A recorded lesson and a delivered lesson are separate states. An injection receipt is evidence of attempted/delivered transport, not proof of model compliance. Before/after project metrics remain observational.

## Embedding and lesson recovery

The live `embedding.enabled` setting controls the embedding dependency across projects. Check its stored value and change history before diagnosing an empty semantic result as an empty knowledge store. Explicit operator lessons remain eligible for delivery while awaiting vector indexing. Judge-generated raw proposals still require their existing review/reinforcement rules. An approved lesson with a `shared:<topic>` topic explicitly opts into cross-project delivery; ordinary project lessons never become global merely because their project is unresolved. Conversation selection uses lexical relevance immediately and cached semantic relevance once the background query embedding is ready, without delaying the proxy request.

A proposed rule is persisted before embedding. Pending proposals retry saved model output with backoff; retries do not spend another model call. The UTC daily proposer allowance is reserved durably before calls, includes failures, and survives process restarts. Evidence that an earlier proposer version stored while a dependency was failing is retained in `memory.lesson_proposal_recovery` and receives one budgeted reassessment (`recovery_state`: `needs_reproposal`, `reproposed` or `obsolete`). It is not silently treated as an accepted rule.

Accepted daily/long-term lessons also receive bounded background reconciliation for missing or obsolete-model relevance vectors; raw lessons remain owned by ordinary consolidation.

Knowledge indexing runs independently every 30 seconds and distributes each batch across projects. Historical turn embeddings also drain every 30 seconds: one 16-turn batch during activity, or up to eight batches after five idle minutes, with a ten-second budget checked between batches. Session/project vector refresh and idle-turn reaping retain their five-minute cadence.

Disabling embeddings through settings requires an explicit audit reason. The settings UI asks for the reason before making the change. API clients must send an `X-Change-Reason` header and an identifiable `User-Agent` or `Origin`, or the change is refused (`api/handlers/embedding_change.rs`); the reason is recorded in settings history.

## Weekly review

The proxy runs `scripts/learning-audit --weekly --sync` itself (the `learning_audit` job of the same scheduler as the skill promotion below, `scheduled_jobs/jobs.rs`), from the checkout it was started in, under `nice` with a 30-minute limit. A checkout without the script cannot run it, so the scheduled jobs need a mike source checkout. It runs once on Mondays, the first time the proxy checks between 01:00 and 06:59 UTC, so a proxy that was down at 01:00 still runs it that morning. The `learning_audit.enabled` setting under Scheduled jobs in `/settings` switches it off, and `GET /api/scheduled-jobs` (with the `scheduled_jobs` row of `GET /api/capabilities`) shows the last run and any failure. The former `mike-learning-audit.timer` is retired and every stack unit install removes an installed copy (`scripts/lib/stack-units.sh`). One machine per database runs the audit: each proxy renews a lease on the job in `llm.worker_leases` (role `learning_audit`), so two machines on one database publish one report for the week. It audits the preceding complete Monday–Monday UTC week. Run `scripts/learning-audit --sync` for a rolling seven-day audit now, or `--end <timezone-aware ISO timestamp>` for a reproducible window. `--weekly` uses the latest Monday 00:00 UTC boundary.

The process performs bounded read-only database queries without model calls. It writes a full JSON report, ranked reuse candidates, a readable report, and a latest pointer under `artifacts/learning-audit/`. `--sync` ingests only that output directory into a dedicated `weekly-learning-audit` knowledge source under the configured Mike project UUID. It does not synchronize the whole repository. Accepted lessons under `artifacts/learning-memory` are synchronized separately by the promoter, as an `accepted-learning-memory` source under each lesson's own project UUID. A failure shows on `GET /api/scheduled-jobs` with the last output lines. The weekly usage audit (`scripts/usage-audit.sh`, price and cache alarms) is the `usage_audit` job of the same scheduler: it runs once on Sundays between 06:00 and 10:59 UTC, one machine per database, and its exit code 1 means an alarm tripped, not that the run failed. The former `mike-usage-audit.timer` is retired and every stack unit install removes an installed copy.

The report includes per-project and global request/tool activity, origin/model breakdowns, missing usage, corrected and accepted labels, lesson embedding/delivery coverage, proposer calls, effect calculation freshness, repeated identical successful input/results, scripts written across sessions, and reuse telemetry. Outcome counts use genuine-turn facts and current projected verdicts whose next-message pointer still matches; missing provenance and stale labels are reported separately. Original capture is kept intact. Each candidate names a source request and tool-use ID; inspect those through Mike before deciding it is redundant. Identical polls and reads can be necessary. Repeated bytes are not claimed token savings.

`GET /api/improvement/exposures?from=<ISO>&until=<ISO>&project=<path>` reports a bounded window of at most seven days (the last seven when `from` is omitted). It associates recorded lesson injections with genuine turns and subsequent captured requests, token usage completeness, tool calls, failed checks, and outcome labels. `whole_turn_failed_checks` counts checks across the entire turn, including checks before a mid-turn injection; it is not a post-injection causal measure. A request shared by several lessons appears in several rows: never sum lesson rows into global savings. The route serves periodic audits and is intentionally not another always-advertised MCP tool.

The report's lesson delivery section compares the two arms of the `mod_lesson_delivery` experiment over the audited week: sessions and genuine operator turns per arm, lessons delivered per turn, the cache-read share of input tokens, and the judge's corrected rate among judged turns, each rate printed with the counts it comes from. The audit reads it from `GET /api/lessons/delivery-comparison` on the running proxy and says so when that build does not have the route. A request that carries the mod's lesson block has a `mod_lessons` entry in its transformation manifest, and the lessons the mod delivered are `memory.lesson_injections` rows with `origin = 'mod'`.

The report's memory verb grammar section counts, per project and for the window, how many requests carried a `<mem:recall>` tag and how many of those led to lessons being delivered (read from the `recall_injector` entry of each request's transformation manifest), how many `<mem:update>` tags the harvester found in replies and how many became lessons or were skipped (read from `memory.harvest_runs`, which has rows only from the deploy that added it), and how many lessons with source `harvester` were created. When neither tag was seen in the window the report carries the finding `memory_grammar_unused`. Reading the recall counts scans a week of request manifests.

When facts change, current live verdicts must match the current next-genuine-message pointer. Changed pointers become eligible for reassessment; stale machine and resumed-session labels are cleared while append-only verdict history and historical as-of reads remain intact.

Normal evaluation and action-effect calculation have independent completion markers. `mike eval rollup --execute` recomputes effects even when the normal rollup already exists. The UI distinguishes `not_computed` from `not_enough_data`.

## Reusable tools and results

Before creating another helper, search the existing scripts and `scripts/tool-reuse list`. Inspect a recipe with `show ID`. `run ID` executes its argv directly, without shell interpolation, and returns a small JSON receipt naming the original exit code and full stdout/stderr artifacts. `--fresh` deliberately recomputes it.

Recipes are explicit validated contracts, not commands mined and executed from captured conversations. Register one with:

```sh
scripts/tool-reuse register --description 'Index user guide headings' \
  --contract 'Read-only; only these documents affect the result' \
  --cwd /path/to/project --dependency docs/user-guide --ttl 3600 guide-headings \
  -- rg -n '^## ' docs/user-guide
```

Keys cover working directory, command/recipe, executable bytes, complete declared dependency content and environment. Missing dependencies, new matching files and content changes invalidate the key. Symlink dependencies are rejected: root the recipe at the real target. A dependency change during execution prevents reuse. Concurrent requests for the same key serialize. Failures preserve their exit code but are retried on the next invocation. Network, database, time-sensitive or incompletely declared operations must use `--ttl 0`; dependency hashes cannot validate external state.

The registry and full artifacts live under `~/.local/state/mike-tool-reuse` (override with `MIKE_TOOL_REUSE_STATE` for isolated tests). Export discoverable documentation with `scripts/tool-reuse export artifacts/learning-audit/tool-recipes.md`, then synchronize knowledge. No credentials are written to receipts: environment values participate only in the hash. Every run/hit is logged for the next weekly audit.

Promote opportunities in this order: reuse an existing tool; consolidate repeated result parsing; validate a narrowly scoped recipe; measure its adoption and outcomes. Preserve the original command exit code. Re-running a verification against changed source is necessary work, not waste.

## Quiet overnight processing and skill publication

The proposer uses one durable UTC-day consumption counter. `judge_lessons.max_per_day` is the daytime allowance. `judge_lessons.quiet_max_per_day` is a larger ceiling available only between `quiet_start_hour_utc` and `quiet_end_hour_utc` (defaults 22 and 4) and after `quiet_idle_secs` (default 300) without primary traffic, including tool continuations. An activity-check failure retains the smaller allowance. Each tick makes at most 40 new model calls; saved-output embedding retries do not consume another call. Equal start/end hours disable the quiet window. The provider governor still enforces the global dollar, rate and call ceilings. Lesson proposals have their own configurable guaranteed budget share; a locally exhausted governor is checked before reserving a durable daily attempt. The quiet allowance is a ceiling, not a promise to spend it. The shape rewrite pass and the placement pass do not draw on any of these allowances: each of their model calls is counted in `maintenance_consumed` on the same daily row and limited by `judge_lessons.maintenance_max_per_day` (default 400, no quiet-window boost), so a maintenance backlog never uses the calls kept for new corrections. The quiet boost (`quiet_max_per_day`) defaults to 0, which leaves it off.

`scripts/learning-promote` materializes accepted lessons as project memory artifacts and synchronizes them under each original project's UUID. Confirmed superseded, archived and expired lessons are excluded. Agent-specific lessons receive separate persona-scoped memory and skills rather than becoming general project instructions. Raw judge candidates remain excluded. Active projects receive small discoverable workflow skills with progressively loaded memory references; validated command recipes receive executable-procedure skills. Files are installed for Codex and Claude Code on the host running promotion.

The proxy itself runs `scripts/learning-promote` (the `learning_promote` job of the in-proxy scheduler in `scheduled_jobs/`, where a further job is one entry in `jobs.rs`), on every machine the proxy runs on, so each machine's checkouts get skills. It runs hourly at :30, from 20:30 to 03:30 UTC, from the checkout the proxy was started in, under `nice` with a 15-minute limit; the stack's systemd unit sets that directory with `WorkingDirectory`, and `deploy-proxy.sh` changes into it before starting the binary. Each proxy promotes for its own machine and nothing is leased. The `learning_promote.enabled` setting under Scheduled jobs in `/settings` switches it off. The last run and any failure show on `GET /api/scheduled-jobs` and on the `scheduled_jobs` row of `GET /api/capabilities`; after repeated failures the job backs off from 30 minutes up to 4 hours. The former `mike-learning-promote.timer` is retired: every stack unit install (`deploy-proxy.sh`, `start-proxy.sh`, `restart-frontend.sh`) removes an installed copy, so it does not run twice. This step is deterministic and does not make LLM generation calls; synchronized memories are indexed by the existing embedding worker. Generated files carry an ownership manifest: manual edits become visible conflicts, never overwrites, and unchanged generated outputs that become obsolete are retired to an archive. The source project memories remain searchable via Mike even on machines without local skill files. Read the actual relevant lessons; the generated skill wrapper is a retrieval aid, not a claim that every lesson is an independently evaluated procedure.

On each run the promoter also measures every skill it owns in its ledger (`~/.local/state/mike-learning-promotion/skill-installs.json`, matched by project and folder, not by name alone) against real use, and posts the result to `POST /api/learning/skill-outcomes`, which stores it in `memory.skill_live_outcomes`. For each skill it counts the `Skill` tool loads in the project since the skill shipped (at most 30 days back), the operator turns that contained a load, and the share of those turns the judge marked corrected, beside the same share over all of the project's judged turns in the same window. A skill is retired, its files archived and the topic held until it gains a lesson, when it was not loaded for 30 days, or when it has at least 10 loads and its corrected rate is above the project's. The next skill draft for a retired topic receives the retired skill's numbers and text as author input, so the topic is rewritten and not repeated. If the proxy cannot store the numbers (an older proxy without the route, for example) the promoter keeps them in its ledger and sends them on the next run. The weekly audit lists them under "Live use of shipped skills", and `memory.skill_evidence_v` joins them to the newest draft's evaluation for the learning observer.
